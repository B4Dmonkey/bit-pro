# A bar named a new identifier the package already had

## What happened

The BIT-39.17 plan detail named the helper it wanted, twice and concretely — in Scope:

> - `cmd/serve.go` — a `claudeBin()` helper reading `BP_CLAUDE`, and `newServeDaemonCmd` passing it
>   to `daemon.Loop` in place of the literal added by the previous bar.

and again in the GREEN step:

> - [ ] `cmd/serve.go`: `func claudeBin() string` returning `os.Getenv("BP_CLAUDE")` when
>   non-empty and `"claude"` otherwise.

`claudeBin` was already taken in package `cmd`. `cmd/testconst_test.go:6` declares
`claudeBin = "claude"`, a test-only constant used by `cmd/cmd_test.go:98,103,104` to build
expected argv. Go test files in the same package share one namespace, so
`func claudeBin() string` in `cmd/serve.go` is a redeclaration and the test binary does not
compile. The bar as written could not go green.

Implemented as `claudePath()` instead — same behaviour, one identifier different — rather than
churn the test constant and its three call sites.

## The gap

Not that the plan picked a bad name. That a plan step can name a **new package-level identifier**
and nothing in the pipeline checks it against the namespace it will land in.

Two things made it easy to miss, and they compound:

1. The colliding declaration lives in a `_test.go` file. Nothing in the production code of
   `cmd/serve.go` hints at it; the name is only visible if you grep the package including tests.
2. The Scope section of the bar listed `cmd/serve.go` only. An implementer who reads exactly the
   scope files the bar names — which is what bit_do instructs — reads the one file where the
   collision is invisible. A scope list is a production-file list; the namespace of a Go package
   is wider than that.

So the failure mode is general: any bar introducing a new function, type, const, or var into an
existing Go package can collide with a test-only declaration that its scope list never points at.
It surfaces as a compile error at the RED step, which is cheap, but it means the stated GREEN step
is not runnable as written and the implementer has to make a naming call the plan should have made.

## Where it would have been caught

A `grep -rn <identifier> <package>/` while authoring the step — cheap, and it covers `_test.go`
files that a scope list does not. bit_plan already reads scope files to write the detail; the
missing move is checking a *newly introduced* name against the whole package rather than only the
file it will live in.

Left open on purpose: whether that check belongs in bit_plan (where the name is chosen, which
argues for there) or in bit_do (before implementing).
