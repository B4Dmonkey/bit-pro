Happened at BIT-20.4, under track BIT-20 ("Kanban-first bp tui: default view, modal paging, expanded detail pane"). Root cause traces back to BIT-20.2 and to the track's own Decisions.

Scope (BIT-20) Decisions section says:
> **Default column and selection.** On open, focus the first non-empty column in the order
> To Do → Doing → Done (in practice almost always Doing). Within that column, default to
> the first *bar* (a dotted child ID) in list order, skipping over track-level rows;
> if the column contains no bars, default to its first row (a track).

Bar BIT-20.2 ("defaultColumn picks the first non-empty column") implemented exactly that
Decision — `for i, c := range cols { if len(c) > 0 { return i } }` — and its first test case's
Behavior field frames it as if Doing were the target itself, not just usually first-non-empty:
> **Behavior:** with Doing non-empty, that's the column an operator lands on — the common
> case (a task actively in progress).

None of BIT-20.2's four test cases ever populated more than one column at once, so the
Decision's literal "first non-empty in *order*" semantics (To Do wins if both To Do and Doing
have tasks) was never distinguished from "Doing wins whenever Doing is non-empty" — the two
only diverge in the two-populated-columns case, which no test exercised.

BIT-20.4 ("New() lands on the Doing column's topmost bar") wrote the walking-skeleton's outer
test with exactly that previously-untested shape — a task in To Do and a track+bar in Doing —
and asserted landing on Doing. Wiring `defaultColumn`/`firstBarIndex` into `New()` and running
it showed the implementation (correctly, per the scope's literal Decision text) lands on To Do
instead, since To Do is non-empty and comes first in the stated order.

What was discovered: the scope's own Decision text ("first non-empty column in the order
To Do → Doing → Done") is the literal spec the implementation follows correctly, but it
silently permits a case — both To Do and Doing populated — that contradicts the walking
skeleton's stated goal ("operator opens bp tui and lands directly on the task they're already
working on"). The Decision was written and accepted without a test or example checking that
specific case, and it reached bit_plan (BIT-20.2) and then implementation without anyone
naming the ambiguity between "first non-empty by order" and "Doing takes priority."
