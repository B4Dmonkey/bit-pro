Two bit_scope mechanisms produced that entry.

The first is the Risks & unknowns template, which requires a
`**De-risk before planning?** Yes / No — why.` line on every unknown, and
which describes an unknown's two honest resting places: "**answered now** —
it becomes a Decision — or **named in Risks, tied to the specific early verse
that resolves it by building**." The entry took the second resting place and
answered the De-risk line "No".

The second is the skill's inline-probe rule: "**An inline probe** you can run
during this scoping session — hit the staging endpoint, read the library's
source, try the command. Cheap and immediate. Run it, then write the
**Decision**. It never becomes a verse, and leaving it as one wastes a whole
planning cycle on something a five-minute check would have settled. Reach for
this first, always." The probe was identified and written into the entry's
`Resolve by` line, but was not run; it was offered to the user in the
handoff message instead:

> Assistant: One risk is open, deliberately: whether a background session in
> a fresh `.claude/worktrees/<name>` parks on a folder-trust prompt. Both
> 2026-08-21 probes did, but in a repo you'd never opened; the 2026-08-24
> config finding suggests trust keys on the repo root. Verse 1 proves it
> either way. If you'd rather not find out there, I can settle it now with a
> throwaway `claude --bg -w bit-probe` in this repo — say the word and I'll
> run it, since it does spawn a real session and create a worktree.
