Happened while running bit_do on BIT-43.2, under track BIT-43 ("Skills walk the MCP
surface"). First noticed by the session that implemented BIT-43.1.

Every bar in this track carries a Migration-checklist step directing the implementer to
hand the draft to the user before it counts as applied.

Bar BIT-43.1 says:
> 3. **Present the draft to the user** for an explicit accept/reject before it counts as
> applied.

Bars BIT-43.2, BIT-43.3, BIT-43.4 and BIT-43.5 each say:
> 3. **Present the draft** to the user for accept/reject.

BIT-43.6 carries the same sentence as step 4, BIT-43.7 as step 2.

Four of those bars pair that step with a `## User verifies` section stating there is
nothing for a human to check:

> BIT-43.1: "none — deterministic. The rewritten skill isn't exercisable until this
> verse's last bar pushes and refreshes the plugin."
> BIT-43.3: "none — deterministic. Verse 2's capability isn't exercisable until its last
> bar pushes."
> BIT-43.4: "none — deterministic."
> BIT-43.6: "none — deterministic. The verse's end-to-end check lands on its last bar."

The remaining three (BIT-43.2, BIT-43.5, BIT-43.7) list real User verifies items, but
those items check the GitHub push and the plugin refresh — none of them checks the draft
accept/reject the Migration step asks for.

What was discovered: bit_do reads `## User verifies` to decide whether a bar stops for a
human, and the bit_bot_dev agent reads the same section to decide whether it may commit
unattended. On the four bars above the two sections give opposite answers about whether a
human gate exists, and the bar text does not settle which one governs. The session
implementing BIT-43.1 had to decide that itself. On BIT-43.2 the question did not arise,
because its User verifies section lists real items.
