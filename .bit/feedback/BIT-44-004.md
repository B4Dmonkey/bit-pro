Happened after BIT-44.5 was committed (d5ca1bd), under track BIT-44 ("Deep research before scope: bit:analyze + bit:ruler"). No bar covers it; it was fixed in its own commit ahead of BIT-44.6.

Scope (BIT-44) says, in its Decisions: "**Research keys to a track the same way feedback does.** The track has to exist (active, completed, or archived), which catches a mistyped ID." And: "The first write creates `.bit/research/<track>/`, the way `feedback_add` creates `.bit/feedback/`."

Bar BIT-44.1 says: "`researchDir(track)` = `filepath.Join(s.root, researchSubdir, track)`". Bar BIT-44.2 says: "In `WriteResearch`, after `NormalizeID`, `if !s.trackExists(track) { ... }` before `MkdirAll`." Neither bar says anything about a track ID that contains path segments.

What happened:
- The coordinator ran the BIT-44.5 user check (`/bit:analyze BIT-44` in a fresh `claude -p --plugin-dir ./bit` session). That analyze pass wrote research notes to `.bit/research/BIT-44/` and reported a possible path escape. The coordinator relayed it: "`trackExists` checks `s.Path(track)`, which uses `pathologize.Join` (`task/store.go:38`). `researchDir` uses plain `filepath.Join(s.root, researchSubdir, track)` (`task/research.go:17`), and `NormalizeID` only uppercases the ID. So a track like `../../BIT-44` might pass the existence check and then write outside `.bit/`." It added: "nobody has reproduced it yet."
- Reproduced with new tests. With track `FOO-1` seeded and track ID `../../FOO-1`: `research_write` succeeded and created `<project>/FOO-1/index.md`, outside `.bit/`. `research_read` with topic `index`, and the topic listing, both succeeded against a folder seeded at `<project>/FOO-1/`.
- The coordinator offered two fixes: build the research path the way `Path` does, or reject path-like track IDs, noting that rejecting would match the user's earlier direction to avoid relative paths. Rejecting was chosen. Building the path like `Path` would have silently mapped `../../FOO-1` onto the real `FOO-1`.

The work required: `researchTrack` in `task/research.go` refuses a track ID containing `..`, `/` or `\` ("track ID %q looks like a path") before normalizing and checking that the track exists. `WriteResearch`, `ReadResearch` and `ResearchTopics` all go through it. Tests: `ResearchWriteRefusesATrackIDThatEscapes` and `ResearchReadRefusesATrackIDThatEscapes` (topic and listing).
