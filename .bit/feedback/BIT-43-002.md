Happened while running bit_do on BIT-43.12, the final bar of track BIT-43
("Skills walk the MCP surface"). Distinct from BIT-43-001, which is about the
`User verifies: none` vs. "present the draft" contradiction.

BIT-43.12 is the track's acceptance test. Its Method opens with:

> - [ ] Confirm everything is pushed. The plugin installs from the default branch, so an
>       unpushed skill edit reaches no project — including the fixture.

and the track's Decisions say the same thing twice more:

> - **Every skill edit goes through skill-creator and ships via GitHub. A local edit that
>   hasn't been pushed doesn't count as done — the plugin installs from the default branch.**
> - **Additive: bash path stays open until Verse 5's real cycle runs.**

So the plan knew about the GitHub coupling. It is written into the scope's Decisions, and
into this bar's first Method step, in plain terms.

What it never did was give that coupling a step or an owner. All twelve bars were
implemented on branch `worktree-agent-a6848e37a1646d392`. The repo's default branch is
`main`, and `origin/main` sits at `f2bc65f release: v1.1.0` — none of the track's work is
on it. `git branch -r --contains worktree-agent-a6848e37a1646d392` returns only the
worktree branch itself.

The measurable consequence: `git grep -nE "bp (task|feedback|instructions)" origin/main --
bit/skills/* bit/agents/*` returns 45 hits; the same grep on the worktree branch returns 1
(an intentional prose example in plan/SKILL.md). `claude plugin update bit@bit-pro`
therefore installs the pre-migration skills — the ones that still shell out. Running the
acceptance cycle against them would exercise the old skills and report a failure that says
nothing about this track's work.

What was discovered: a bar whose verification depends on an action no bar performs cannot
be run when it is reached, and nothing in the pipeline catches that at plan time. Every
bar's checks are scoped to that bar, so "is the thing this bar verifies actually reachable
by the time we get here?" is never asked. Here the missing action is a merge to the default
branch, which is a human decision and reasonably outside a bar — but the plan recorded it
only as a constraint in prose, not as a step, a dependency, or a named hand-off. The
distinction that matters: BIT-43-001 is about two sections of one bar disagreeing;
this is about the plan stating a precondition it never schedules.
