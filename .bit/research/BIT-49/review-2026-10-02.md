## 4. Feedback and retro in the shared store
- **Today:**
  - retro lists and reads `.bit/feedback/*.md` with file tools (`retro/SKILL.md:18,29`), writes `.bit/retro/<track-or-album>-proposals.md` directly (:27, :76), and globs `.bit/retro/*-proposals.md` to de-duplicate (:110).
  - learn takes a path or pasted content (:16).
  - The feedback skill only uses `feedback_add` (`feedback/SKILL.md:12`).
- **Tools needed:**
  - retro: `feedback_list(track?)` (current project only), `feedback_read(id)`, `retro_list()` (de-dup), `retro_write(name, body)`.
  - learn: `retro_list()` (all projects), `retro_read(name)`.
  - **Under-specified:** `feedback_read` for another project's note. **Default:** refuse unless the note's `project` is the current one. Otherwise `feedback_list`'s default is bypassable.
  - **Under-specified:** `retro_list` scope. learn needs all projects, and retro's de-dup is fine with all, since proposals are generalised, but the list exposes other projects' codes. **Default:** all projects, each row showing `project`.
  - **Under-specified:** `retro_write` replace vs create-only. **Default:** replace by name, like `research_write`. The `commits` list (BIT-47) appends on a later write.
- **Feedback filename collisions:** none possible. `<TRACK>-NNN` embeds the code, codes are UNIQUE and contain no `-`, and removed codes stay reserved, so a flat top-level `feedback/` is safe. `nextNoteSeq`'s glob `<TRACK>-*.md` with an anchored regex doesn't cross tracks (`BIT-4-*` can't match `BIT-45-001.md`).
  - The store change is structural: `feedbackDir` hangs off the project `s.root` (`task/feedback.go:15-17`), but `trackExists` must still use the project store. The feedback dir needs the data root separately (a new field or a separate type).
- **Retro name:** `<CODE>-<track-or-album>-proposals` doubles the code for a track (`BIT-BIT-49-proposals`), since track IDs already carry it. A retro over "several tracks" has no defined name. **Default:** the server prefixes `<CODE>-`, and the skill passes the track ID, `album`, or a short slug for a multi-track retro. Accept the redundancy.
- The `feedback_add` description ("keys to a track … whose ID has no dot", `cmd/serve_mcp.go:95`) is looser in code: `resolveTrack` accepts a bar ID, because `trackExists` stats `Path(id)`. That's pre-existing and harmless.
