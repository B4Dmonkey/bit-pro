## 3. bit:commit feasibility
- **Permission is real, but `ask`, not deny.** `~/.claude/settings.json:15-21` `ask`: `Bash(git commit *)`, `Bash(git push *)`, `Bash(git add *)`, `Bash(git merge *)`. The track says the settings "reject" the commit tool; they *prompt*. Correct the wording. Consequences:
  - `git add` also prompts, so add + commit + push can be 3 prompts per bar. Default: one Bash call `git add <files> && git commit -m …` after the prose ask (unverified whether the harness then prompts once or per sub-command; check in the dev sandbox).
  - **Headless/background runs** (`claude -p`, `claude --bg '/bit:do …'`, which bot-dev's description names) can't answer an `ask` prompt. Unknown how `--bg` surfaces it. bot-dev "stops and asks" only works in an attached session. Settle in a spike or default: bot-dev's description drops the `--bg` example and says it needs an operator to approve commits.
  - Auto mode / `--dangerously-skip-permissions` may auto-allow; the prose ask (already a Claude default) covers that.
- **Recording**: the skill runs `git commit` via Bash in the session cwd, then `git rev-parse HEAD` and `git rev-parse --abbrev-ref HEAD` (not ask-listed), then one `task_update` with `commit`, `branch`, `status: done`. Detached HEAD returns `HEAD`. Default: record branch empty then. Alternative: the MCP handler fills sha/branch from BIT-49's helper if the skill passes nothing. The skill-reads-it route needs no server change beyond the Patch fields.
- **Nothing to commit** is likely in v2: `.bit/` changes no longer land in the repo, so a spike or research-only bar may have an empty diff. `git commit` exits 1. Not covered by any decision. Default: tell the operator there's nothing to commit and, on their OK, mark the bar `done` with empty `commit`. Never `--allow-empty`.
- **Pre-commit hooks**: this repo runs pre-commit with `trailing-whitespace`, `just fmt`, `just lint`, `just test` (`.pre-commit-config.yaml`). Formatter hooks modify files and fail the commit. Default: report the output, re-stage, and ask again. Never `--no-verify`. The bar stays `doing` until a commit succeeds.
- **Files outside the repo / no git** (`acme/`-style, or a bar editing `~/.claude`): `git rev-parse --is-inside-work-tree` fails. Default: skip the commit, say so, mark `done` with empty git fields after the operator's normal verification. Multi-repo bars (one folder, several repos) are out of scope; say so.
- **Unwind and follow-ups after a commit** (do `:75`, `:79`, `:122`): the commit can't be unwound by setting `doing`. Default: the commit stays; the fix is a new commit through bit:commit, which overwrites the bar's `commit` with the newest sha. Note for BIT-50: squash matching uses bar subjects, so a follow-up commit should reuse the bar's subject (or BIT-50 accepts extra subjects).
- **Approval**: `task_update` with `commit`/`branch` must stay out of `contentChanged` (store `:298`). Confirmed as needed.
- **Skill naming**: existing skills use `name: bit_do` style frontmatter in `bit/skills/<dir>/`. A new `bit/skills/commit/` is exposed as `bit:commit`. Follow `name: bit_commit`.
- **Commit message heading**: bars say `## Commit (user)` today. Reading either heading is already a decision.
