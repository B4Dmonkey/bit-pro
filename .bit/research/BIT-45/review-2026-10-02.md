## `bp add` / `bp list` end to end (Q4)
`bp add <path>` (`cmd/add.go:26-79`):
1. Resolves `abs`, then calls `db.Open()` on the v1 path (it migrates on open).
2. Calls `ProjectExists(abs)`. If the path is already registered, it prints "already added" and returns. It does no re-wiring.
3. Reads `<abs>/.bit/config.toml` `prefix` as the default code.
4. Prompts for the code. An empty answer is an error. Otherwise it uppercases the code (`task.NormalizeID`), with no format check.
5. Only if `<abs>/.bit` is missing, it calls `writeClaudeWiring(cmd, run, abs)` (`cmd/init.go:51-71`).
6. Calls `CreateProject` and prints "added CODE abs".

Nothing in `add` touches the daemon, so after removal only the Short text changes. The simulation confirmed the `add` tests pass unchanged. `bp list` then prints `CODE\tPATH` and the TUI keeps browse, reload and approve. The track's claims hold.

**Question (pre-existing, not caused by BIT-45; intentional?):** `writeClaudeWiring` writes `settings.json` under `abs` (`cmd/init.go:52`). But `SyncPlugin` (`plugin install/update --scope project`) and `RegisterMCP` (`claude mcp get/add bit`, local scope) run through `claude.Runner`, which has no dir (`claude/sync.go:10-13`), so they act on the **process cwd**, not on `abs`. So `bp add /other/repo` run from elsewhere wires the plugin and MCP for the cwd's project. The tests only exercise `bp add .` after `t.Chdir` (`cmd/add_test.go:66,81`), so this path is untested. BIT-48 replaces this with user-scope wiring, so it probably only matters if someone dev-tests `bp add <other path>` on `v2` before BIT-48. Combined with the HOME sandbox rule, it would act on whatever directory the dev run's cwd is.
