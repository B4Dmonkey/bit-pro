## 2. The landing ladder against real git

### Rung (a): bug in the landing-commit formula
- `merge-base --is-ancestor <h> <trunk>` is well defined and handles true merges (`landing-ladder` is confirmed).
- **Topic `merge-commit`'s formula `git rev-list --first-parent --ancestry-path <h>..<trunk> | tail -1` is wrong when the feature branch merged trunk back in** before it was merged. Scratch repo: main m1, m2, m3, `Merge branch 'feat'` (--no-ff), m4. feat: b1, `Merge branch 'main' into feat`, b2. Results:
  - b2 → `m4`, `Merge branch 'feat'` → tail = the merge (correct);
  - **b1 → empty output.** With `--first-parent`, the ancestry path is computed over the first-parent graph only, and b1 reaches the merge only through the back-merge. An empty result fed to `git log -1` silently returns HEAD (m4), which is the wrong anchor.
  - Back-merges are real here: `origin/worktree-bit-39` contains `97a5279 Merge remote-tracking branch 'origin/main' into worktree-bit-39`. v2 will likely merge main in before cutover.
  - **Correct, plumbing-only rule:** landing(h) = the oldest commit in `git rev-list --first-parent <trunk>` that is also in `git rev-list --ancestry-path <h>..<trunk>` (no `--first-parent`). Equivalently, it's the oldest first-parent commit X with `merge-base --is-ancestor h X`. When h is itself on the first-parent chain, landing(h) = h. This gave b1 → `Merge branch 'feat'` and m3 → m3 in the scratch repo. Track landing = the newest landing(h) by first-parent index. It's well defined, because every landing(h) is on one chain.
- A fast-forward merge of v2 (main still at the v2 base, `6a1d345`) puts the bars on the first-parent chain directly. That's handled.

### Rung (b): squash bodies in this repo
- A multi-commit squash looks like this. Subject: `<PR title> (#N)`. Body: one `* <subject>` line per branch commit, each followed by that commit's own body paragraphs (`git show -s 54abfeb`). Committer `GitHub`, single parent. Matching must parse lines starting with `* ` exactly. A raw `git log -F --grep` also hits prose inside the bodies, so use it only to find candidates.
- `* subject` matching works on real history. All 3 subjects on `origin/worktree-bit-31` that aren't on main (`007fd0e`, `f3dc5e6`, `aa237a1`) are found in `4cf6137 Worktree bit 31 (#5)` only.
- **A track spanning two squashes is real. Under the decided "every bar's subject in one squash" rule it falls to asking for the PR.** BIT-31 (bars .1–.4, in `.bit/completed/`) landed bars 1–3 in #5 and bar 4 as the single-commit squash `e59da6e fix(tui): render play-prompt overlay in modeList (#6)`.
- The duplicates are confirmed and sharper than recorded. #17's tree is identical to #16's (`git diff --stat ad04ca4 54abfeb` is empty), and both list the same 11 `* ` lines. #15 is a strict superset of #14 (9 ⊂ 16 lines), because the branch kept going after #14 merged. So "earliest squash containing all" picks #16 (correct) and #15 for the bit-39 tail (correct).
- Subjects are reliable only when they're specific. bar subjects here are `type(scope): …`. The risks are generic subjects (`chore(bit): …`) and a PR title edited before a single-commit squash.

### `(#N)` lookup
- It's unambiguous on this history. `git log main -F --grep="(#N)"` returns exactly one commit for every N tested (1, 2, 3, 6, 16, 17), and nothing for 18. No commit has `(#N)` outside its subject.
- To keep it well defined, anchor in Go on the subject ending ` (#N)` and on the first-parent chain only. Otherwise a revert subject (`Revert "… (#6)"`) or a body mention would also match. `(#1)` doesn't match `(#17)`, because the `)` delimits it. If more than one commit matches, ask the operator.
- True merges say `Merge pull request #N from …`. There are none here, but matching that prefix is cheap.

## 3. Completion flow vs the store

- `Store.Load`/`Path` read only `tasks/` (`task/store.go:37-39,164`), and `Update` starts with `Load` (`:272-276`). So **`task_update` can't write to a filed task**: it errors, and it doesn't resurrect the task, because `Save` would only run after a successful `Load`. A consistent order:
  1. `task_landing` (read-only).
  2. With the operator's consent, `task_update` unfinished bars → `done`.
  3. `task_update` repoints bars (`commit`).
  4. `task_update` sets the track to `done` and ticks the verses.
  5. `task_complete{id, commit, branch}`.

  The body states this order, and it's consistent. Re-check after BIT-46's JSON store, which keeps the "filed = moved" model.
- A side effect that already happens today: ticking verses with a `body` edit revokes the track's approval (`task/store.go:298-303`). This is harmless at completion, but don't be surprised by it.
- **"Archive" has no named tool.** The not-done branch offers "archive or keep". The existing archive path is the `task_delete` MCP tool → `Store.Relocate(id, force)` → `archive/tasks/` (`cmd/serve_mcp.go:433-441`). A track with unfinished bars needs `force: true`. Default: name `task_delete` (force when bars are unfinished) in the skill.
- **The BIT-46 `bp remove` interaction is consistent.** BIT-46 already archives "tracks whose bars are all done but which were never completed". Under BIT-50 that is every signed-off but unlanded track, which is what the operator wants, because unlanded work is surfaced by `remove`'s outstanding-work note. There's no conflict, but `remove`'s note should probably list "done, not completed" tracks separately from not-done ones. That's a BIT-46 wording nit.
- **The CLI `bp task complete` is under-specified.** It still calls `Store.Complete` with no landing check. Default: keep it as the manual escape hatch (it files without a landing commit), and say so in its help text.
- **Skill conflicts:**
  - BIT-47 owns do's close-out (`:89-100`) and "Commit" (`:129`).
  - BIT-50 owns the "Track status" sentence (`:95`), the compaction pointer (`:100`), Track sign-off (`:102-110`), `:131` and the description (`:3`).

## 4. Verse shape

- **Verse 1 works on its own.** It must also refuse when any bar isn't `done` ("finish or mark these bars first"), because the partly-done check-in is Verse 2's.
- **Gap: the no-git folder case** ("files the track with no landing commit after the operator confirms", in Decisions) belongs to no verse. Default: put it in Verse 2, next to the other operator check-ins.
- **Gap: tracks with no bar hashes.** Every pre-BIT-47 track, BIT-45/46/48/49 themselves included, has bars without hashes, unless BIT-49's migrate stamped them. Those reach "can't tell" and only Verse 4 completes them. Default: either move Verse 4 ahead of Verse 3, or accept that they're completed with `bp task complete` (the CLI hatch) until Verse 4 lands. Squashes are historical here (none in the last 20 commits), so Verse 3 has the least near-term value. Suggested order: 1, 2, 4, 3.
- **Squash rule.** Change "every bar's subject in one squash" to a **per-bar** rung (b). Each bar not on trunk lands at the earliest first-parent squash whose `* ` lines or stripped subject contain its subject, and that squash's committer date is after the bar's commit date. Then:
  - Track landing = the newest of the bars' landings.
  - Bars repoint to their own squash.
  - This covers BIT-31 (#5 + #6) and mixed direct+squash tracks, and keeps the earliest-duplicate rule.
  - The "all in one" rule can't see either case, and its generic-subject guard is covered by the date check plus per-bar specificity. If the operator keeps the one-squash rule, note that BIT-31-style tracks fall to Verse 4.
- **`task_landing` is under-specified.** bit:plan would have to guess the shape. Suggested defaults:
  - Input: `{id: <track>, pr?: int, commit?: string}`. `pr` or `commit` is Verse 4's answer, checked on trunk.
  - Output:
    - `{trunk: "origin/main"|"main"|"", branch: "main", verdict: "done"|"partly"|"not_done"|"cant_tell"|"no_git", landing: <sha or "">, shallow: bool}`;
    - `bars: [{id, status, commit, class: landed|squash|pushed|local|unresolvable|no_hash, landing, remotes: [...]}]`;
    - `unfinished: [ids]`.
  - It never writes. The skill does every write using `bars[].landing`.
  - Use full 40-char SHAs. BIT-47 should record full SHAs as well. Abbreviated ones can become ambiguous.
  - The track's `branch` is the short trunk name `main`, never `origin/main`.
  - On "partly", when the operator proceeds: landing = the newest landing among landed bars, and unlanded bars keep their own hash.
  - For a Verse 4 answer: the track commit = that commit, and only bars with no hash or an unresolvable hash are repointed to it.

## 5. Hazards for planning and implementation

- **Worktrees:** fine. Refs and objects are shared through the common git dir, so `git -C <session dir>` gives the same answers from a worktree as from the main checkout. A deleted, unpushed worktree branch leaves its commits "local only" until gc, then "unresolvable".
- **No origin:** trunk = local `main`, so local commits count as landed. That's consistent with the decision, but the message must not say "push".
- **Shallow clone:** is-ancestor and cat-file give false "unresolvable" or "not landed" answers. Default: report `shallow: true`, and add "fetch --unshallow" to the retry message.
- **Detached HEAD:** irrelevant to completion, which never reads HEAD. It only matters for BIT-47's bar `branch`.
- **Stale origin (no fetch):** already decided ("fetch/pull/push and retry").
- **v2 itself landing:**
  - A plain merge or a fast-forward keeps the hashes valid. Use the corrected first-parent rule above, especially if main was merged into v2 first.
  - A rebase of v2 makes every hash unresolvable, so it falls to Verse 4.
  - A GitHub squash of v2 produces one huge `* ` list. **Unknown:** whether GitHub truncates very long squash commit lists. Check before relying on rung (b) for v2.
- **Can't dogfood before cutover:** nothing on `v2` is on `origin/main` until cutover, so every real BIT-50 run during development says "not landed". The scratch-repo-with-bare-origin decision is the only test path. Plan fixtures for: direct, ff-merge, true merge with a back-merge, single-commit squash, multi-commit squash, duplicate squash, two-squash track, rebase, shallow, no origin.
