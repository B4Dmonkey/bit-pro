## 2. How `claude` is invoked; testability
- `claude.Runner` (`claude/sync.go:10`) is `func(ctx, name, args...) error`. **No stdout, no exit code**; `ExecRunner` (`:12-19`) folds output into the error string. The only runner returning `(out, code, err)` is `DirRunner` in `claude/dispatch.go:14`, which **BIT-45 deletes**.
- Seam: `newRootCmd(run claude.Runner, ...)` (`cmd/root.go:128`), passed to `newAddCmd(run)` (`cmd/add.go:21`). Tests stub it via `runWithRunner` (`cmd/cmd_test.go:43`) and the `recorder` in `claude/sync_test.go:22-34`. So the ensure step is fully testable without a real `claude`.
- `cmd/add_test.go` already sets `HOME` to a temp dir (`:19,64,148,191,226`), so a reader of `~/.claude.json` via `os.UserHomeDir()` is isolated in tests for free. Follow `claude/plugin.go`'s pattern of taking `home` as a parameter.
- Exact commands (bp keeps calling `bp` by name, as today; do **not** bake in `os.Executable()`, which would pin a dev build path into user config):
  1. `claude plugin marketplace add B4Dmonkey/bit-pro`
  2. `claude plugin marketplace update bit-pro`
  3. `claude plugin install bit@bit-pro --scope user`
  4. `claude mcp add -s user bit -- bp serve mcp` (only if no user entry)
- Note: `claude mcp get` health-checks by **spawning the server** (probe showed `Status: ✘ Failed to connect` for `/usr/bin/true`). Another reason not to use it.

## 4. "Check for a user-scope entry itself"
- **Verified:** user-scope MCP servers live at the **top-level `mcpServers`** of `$HOME/.claude.json`. Probe: a sandbox `.claude.json` with only top-level `mcpServers.bit` made `claude mcp get bit` report `Scope: User config (available in all your projects)`. Local-scope entries live under `projects[<abs path>].mcpServers` (real file).
- Recommended check: parse `<home>/.claude.json`, test `mcpServers.bit` exists. Present → skip step 4. Absent file or no key → run `mcp add -s user`.
- Risks:
  - **R1 file is Claude-owned and hot.** ~200 KB, rewritten by every running session. A torn read gives invalid JSON. Default: on read or parse error, attempt the add anyway; a duplicate makes `mcp add` exit 1, which surfaces through the existing "report the failed step and print the commands" path. Read-only, so no corruption risk.
  - **R2 `CLAUDE_CONFIG_DIR`** (unset here) is believed to relocate `.claude.json`. **Not verified.** Default: ignore it; worst case is R1's fallback.
  - **R3 undocumented format.** The key is stable today, but it's internal. Accept it; the fallback limits the damage.
  - Alternative rejected: string-matching "already exists" in `ExecRunner`'s error text (fragile; Runner returns no exit code). Running `mcp get` from an empty temp dir would be scope-clean, but Runner has no `Dir` and `get` spawns the server.
- Only step 4 needs a pre-check. Steps 1-3 are idempotent exit-0 per `soundness-2`.

## 5. Placement for BIT-49
- `writeClaudeWiring` is in package `cmd` (`cmd/init.go:51`). BIT-49's `bp migrate` is a new `cmd/migrate.go` (BIT-49 Verse 2 Touches), the same package, so an unexported cmd-level helper is reachable. Suggested split: `claude.EnsureGlobal(ctx, run, home) error` holds the four steps and the `.claude.json` check, and returns an error naming the failed step. A thin cmd helper (e.g. `ensureGlobalWiring(cmd, run)`) prints progress plus the manual commands on failure, and `add` and `migrate` both call it. Put the four command lines in one exported var/func so the failure message, tests and README stay in sync.
- **Missing Touches:** `cmd/init.go` (where BIT-46 leaves `writeClaudeWiring`; the file may end up holding only the helper, so delete or rename it), `cmd/add_test.go:85-111` (output text, settings.json assertion, calls), `cmd/init_test.go` if BIT-46 left any wiring tests, `claude/{sync,settings,plugin}_test.go`, `cmd/root_test.go:153`, `cmd/testconst_test.go`, and `cmd/root.go:32` `claudeDir` (dead once the settings path goes).
