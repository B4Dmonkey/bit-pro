## Why
Once BIT-46 has moved each project's tasks and research into the central store, three things still stop v2 from replacing v1.
- Feedback and retro are still per-project files. retro reads `.bit/feedback` and writes `.bit/retro` directly (`bit/skills/retro/SKILL.md:76`), so it breaks as soon as `.bit/` stops being the store. learn takes a proposals file by path or pasted text (`bit/skills/learn/SKILL.md:16`), the v1 hand-carry model, so in v2 it has nowhere to find proposals (corrected 2026-10-02: learn reads no `.bit/` path itself).
- The operator's real projects can't reach v2 at all. There's no way to bring a v1 `.bit/` across, so the operator can't trial v2 on live work while v1 keeps running.
- Skills, agents and help text still send Claude to `.bit/`.

## Summary
Feedback notes and retro proposals move to shared top-level `feedback/` and `retro/` folders with a `project` field. retro and learn reach them through new MCP tools. `bp migrate` copies a v1 project into the central store without touching the source, then registers it and, on a first migration, ensures the global wiring. A final sweep removes `.bit/` from skills, agents, the plugin description, MCP descriptions, help text and the README.

## Decisions
- **Depends on BIT-46 (store and format) and BIT-48 (the global wiring step, which migrate reuses).**
- **Feedback and retro live in top-level `feedback/` and `retro/` folders with a `project` field.** retro and learn reach them only through new MCP tools, never by reading files directly (BIT-45 topic `skills`). BIT-46 reserves the codes `FEEDBACK` and `RETRO`, so no project dir can collide with these folders.
- **The new MCP tools are `feedback_list`, `feedback_read`, `retro_write`, `retro_list` and `retro_read` (Claude default).** These are the tools BIT-45 topic `skills` found retro and learn need. `feedback_add` keeps its signature (MCP `{track, body}` returning `{path}`, `cmd/serve_mcp.go:169-176`; CLI `bp feedback add <track> -d`), and the server fills in `project`.
- **`feedback_read` refuses a note that belongs to another project (Claude default, 2026-10-02).** It's the same confidentiality line as `feedback_list`'s default.
- **`retro_list` lists every project's proposals and shows each one's project. `retro_write` replaces a proposal of the same name (Claude default, 2026-10-02).** learn reads every project's proposals (below), and a re-run of retro on a track rewrites its proposals, as writing the file does today.
- **A new feedback note never overwrites another (Claude default, 2026-10-02).** `AddNote` writes with `os.WriteFile` today (`task/feedback.go:74`), which overwrites. In a shared folder, two worktrees of one project can pick the same next number. The note is created exclusively, and on a clash the next number is tried.
- **Retro proposals are records like the rest.** They carry the same `commits` list that BIT-46 Verse 2 gives research topics and feedback notes. The store's retro write takes the `commits` value from its caller like BIT-46's other writes, empty here, so BIT-47 only fills it in (Claude default, 2026-10-02).
- **`feedback_list` returns only the current project's notes by default.** Notes quote exchanges verbatim, and retro promises it's safe to run inside a confidential client project, so retro in one project must never read another project's raw notes.
- **There's no cross-project option on `feedback_list` in this track (Claude default).** Nothing needs one yet, and leaving it out is the safe side of the confidentiality decision.
- **Retro proposal file names include the project code.** A name keyed only by track or project name could collide with another project's proposals in the shared `retro/` folder. The name is `<CODE>-<track-or-album>-proposals` (Claude default), which extends today's `<track-or-album>-proposals.md` (`bit/skills/retro/SKILL.md:76`).
- **The server adds the `<CODE>-` prefix, and a name that already starts with `<CODE>-` is kept as it is (Claude default, 2026-10-02).** v1 names keyed by a track ID already start with the code (e.g. a `ACME-1-ACME-4-proposals.md` in another project), and doubling it would read `ACME-ACME-1-…`. migrate applies the same rule.
- **learn reads every project's retro proposals.** Proposals are already generalised when retro writes them. learn's description is rewritten: today it says proposals are "carried over by hand" and learn runs "never inside the project the proposals came from", which describes the v1 model. Its body says the same and is rewritten too: `learn/SKILL.md:8`, `:16`, `:22`, and retro's matching text at `retro/SKILL.md:10` (a pointer to a "Handoff" section that doesn't exist), `:102` and `:123` (corrected 2026-10-02). How learn works beyond that is revisited later.
- **On the dev branch, retro and learn are broken from BIT-46 until Verse 1 lands.** This is accepted.
- **`bp migrate` copies and never touches the source.** It stages, verifies (counts, metadata, byte-equal bodies), then commits, registers the project last, and ensures the global wiring. That makes it idempotent and easy to roll back. It carries `completed/` and `archive/` across as they are, which keeps their IDs reserved (BIT-45 topic `migrate`). That includes bars sitting in `archive/tasks/` whose tracks are in `completed/`, partial `order` lists, and feedback for archived tracks, all present in bit-pro's `.bit/` (fact, 2026-10-02).
- **migrate's verify includes a byte-for-byte round trip of every task file (Claude default, 2026-10-02).** `task.Parse` silently drops frontmatter keys it doesn't know. Re-serialising each parsed task and comparing it with the source catches that. All 435 task files in bit-pro's `.bit/` round-trip exactly today. A file that doesn't, or doesn't parse, stops the migration and is listed.
- **Re-running migrate on a registered project doesn't set up the wiring (operator, 2026-10-01).** Only the first migration, the one that registers the project, ensures it. The wiring is global and owned by BIT-48.
- **A re-run on a registered project stops with "already migrated" and changes nothing (Claude default).** That's the idempotency the copy-only decision promises (BIT-45 topic `migrate`, step 2).
- **Migrate trials run only in a sandbox (Claude default, 2026-10-02).** A trial can't be refreshed in the real store: a re-run says "already migrated", and `bp remove` keeps the code.
- **migrate on a removed project's path refuses and points to `bp add` (Claude default, 2026-10-02).** Reviving is `bp add`'s job (BIT-46).
- **migrate refuses a code that belongs to another project, including a removed one (Claude default).** This is the same rule `bp add` follows (BIT-46). It also applies BIT-46's code format and reserved names (Claude default, 2026-10-01).
- **In a Claude worktree, migrate reads the main checkout's `.bit/` (Claude default).** v1 kept state there for worktree sessions (BIT-45 topic `migrate`, step 1). It finds it with the main-checkout cut BIT-46 keeps from `bitdir`. Git facts still come from the session dir.
- **Run from a subfolder, migrate walks up to the nearest `.bit/` (Claude default, 2026-10-02).**
- **migrate registers the folder that holds the `.bit/` it reads (Claude default, 2026-10-01).** In a Claude worktree that's the main checkout, never the worktree, so the project resolves from the main checkout and from every worktree under it.
- **migrate prints the cleanup step (`git rm -r .bit` where `.bit/` is tracked, otherwise removing the folder) but never runs it (Claude default).** It never touches the source, and cleanup is on the operator's cutover checklist. Where `.bit/` is tracked, the message also says to delete the untracked files the `git rm` leaves behind (bit-pro has 153 today, e.g. BIT-45..50).
- **migrate refuses a `.bit/` whose IDs aren't normalised to uppercase** (v1's `update/normalize.sh`). Mixed-case IDs would collide in uppercase dirs on case-insensitive APFS. The check reads the raw files, because `task.Parse` uppercases IDs as it reads them (`task/task.go:48-51`).
- **migrate stops and lists any unknown files under `.bit/`.** This gets revisited near the end. The pre-2026-07-29 flat layout, deleted tasks as `archive/<ID>.md`, counts as unknown. The operator normalises it first, as bit-pro did by moving all 126 of them to `completed/` in `95aec1f` (Claude default, 2026-10-02). bit-pro's own `.bit/` has no unknown files.
- **Values migrate can't know default to migration time.** Timestamps get the migration time.
- **What migrate writes for git info, per record kind (operator, 2026-10-01).**
  - Tracks and bars, in `tasks/`, `completed/` and `archive/`: `branch` gets the branch at migration, and `commit` gets HEAD at migration.
  - Research topics, feedback notes and retro proposals: `commits` gets one entry, `{sha: HEAD at migration, branch: branch at migration, at: migration time}`.
  - In a folder with no git, every git field stays empty.
  - The BIT-45 research topics `migrate`, `json-schema` and `history-anchors` predate these decisions and still say otherwise (empty anchors, git-log timestamps, `head`, a project path in records).
- **This track owns a small git helper that shells out to the `git` CLI.** migrate uses it to read HEAD and the branch, BIT-47 and BIT-50 extend it, and tests stub it. Git 2.54 on this machine supports `rev-parse --path-format=absolute` (fact, 2026-10-02).
  - **Git facts come from the session dir, not the registered path (operator, 2026-10-01).** The session dir is the worktree the session runs in: `CLAUDE_PROJECT_DIR` for MCP, and the current folder for the CLI. A Claude worktree has its own branch and HEAD (BIT-45 topic `history-anchors`).
  - A git error, or a folder with no git, gives empty values and never fails the command (Claude default, from BIT-45 topic `history-anchors`).
- **The sweep only removes the `.bit/` staging lines from do and bot-dev (operator, 2026-10-01).** It doesn't preserve or reword bot-dev's unattended commit-without-asking behaviour. In v2, bot-dev stops and asks the operator's permission before every commit, through BIT-47's commit skill, and BIT-47 rewrites that text. The staging lines are `do/SKILL.md:75` (the end of the line, which relies on `.bit/` being committed with the code) and `:99`, and `bot-dev.md:27-28` (fact, 2026-10-02: `:75` was missing).
- **"Never hand-edit `.bit/tasks`" becomes "the `mcp__bit__*` tools are the only way in", without naming a path (Claude default, 2026-10-02).** It appears in seven skills and agents, plus `check/SKILL.md:12`.
- **The sweep changes only the wording of lines BIT-47 and BIT-50 later rewrite (Claude default, 2026-10-02).** do's description and sign-off, and the complete skill (`complete/SKILL.md:3,8,12,23,30`), are edited by this track, then BIT-47, then BIT-50. Later tracks anchor on section names.
- **The sweep covers the user-facing docs, and leaves design notes as history (Claude default, 2026-10-02).** `README.md` and `hierarchy.md` are swept. `mcp-notes.md` and `automation-notes.md` are historical design notes and aren't (BIT-45 deletes `automation-notes.md` and `abort-run.md`, and trims the daemon parts of `mcp-notes.md`).
- **Every bar that edits a skill or agent validates it (Claude default, 2026-10-01).** It runs skill-creator's `quick_validate.py` on each changed skill and `claude plugin validate ./bit` (memory `bit-skill-edits-run-skill-creator`; the kebab-case `name:` failure is known noise). The analyze evals that name `.bit/` are updated with the sweep (`analyze/evals/evals.json:14` is the only one).
- **Dev runs follow BIT-46's rule (Claude default, 2026-10-01):** never `just install` on `v2`, and sandbox `XDG_DATA_HOME` and `HOME`. Migrate is tried against a copy of a real `.bit/` in the sandbox (bit-pro's and example's), and skills through `--plugin-dir`. A client project's `.bit/` isn't opened or copied for trials.
- **Each bar leaves `just lint` and `just test` green (Claude default, 2026-10-02).** That is what the pre-commit hook runs.
- **Cutover belongs to the operator.** The operator alone decides when v2 is ready and merges the branch, and no track gates it. Migrating each project is a step on the cutover checklist in `v2-sketch.md`, run when the operator chooses.
