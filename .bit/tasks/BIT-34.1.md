## **Verse 1**

Re-enqueueing the same target stops writing a second row: a unique index on
`(project_id, target_id)` plus `INSERT OR IGNORE` makes the write idempotent in the
database, so no caller can produce a duplicate regardless of how fresh the TUI's reload is.
Nothing in the queue is enqueued more than once yet, so this lands before the later verses
turn one gesture into N rows.

## Scope
- `db/migrations/<new>.sql` — new dbmate migration: `CREATE UNIQUE INDEX` on
  `queue(project_id, target_id)`; the down migration drops it. Create the file with
  `just db-migrate queue_unique_target` so the timestamp prefix matches the existing files.
- `db/queries/queue.sql` — `EnqueueTask` becomes `INSERT OR IGNORE INTO queue ...`.
- `db/orm/queue.sql.go` — regenerated by sqlc, not hand-edited (`just db-gen-queries`, which
  `just test` and `just lint` already run as a dependency).
- `db/queue_test.go` — the new test lives beside `TestQueue_EnqueueAndList`.

The live `queue` table is empty and `queue` has no existing unique index, so the index
creation has no pre-existing duplicates to trip over and needs no data step.

## TDD cycle

1. **Write test (RED):**
   - [ ] `TestQueue_EnqueueIsIdempotent` — table-driven over the three cases below, each
         against a fresh temp-`HOME` DB the way `TestQueue_EnqueueAndList` already does
         (`t.TempDir()`, `t.Setenv("HOME", ...)`, `t.Setenv("XDG_DATA_HOME", "")`, `db.Open()`).
     - **Behavior:** the queue holds at most one row per `(project, target)` pair, and a
       repeat enqueue is a silent no-op rather than an error or a second row.
     - **Setup:** one project at `/tmp/proj` (`CreateProject` + `GetProjectByPath`), then:
       - `same target twice` — `EnqueueTask{ProjectID: p, TargetID: "BIT-33.1", TargetTyp: "bar"}`
         called twice.
       - `distinct targets, one project` — `BIT-33.1` then `BIT-33.2`, same project.
       - `same target, two projects` — a second project at `/tmp/proj2`; `BIT-33.1` enqueued
         under each.
     - **Assertions:** both `EnqueueTask` calls return `nil` error in every case;
       `ListQueueByProject` returns 1 row for `same target twice` (`TargetID == "BIT-33.1"`,
       `TargetTyp == "bar"`), 2 rows for `distinct targets, one project` in insertion order,
       and 1 row per project for `same target, two projects`.
     - **Boundary:** the uniqueness key is the *pair*. Case 1 is the duplicate at the point
       the index must bite; cases 2 and 3 sit either side of it — varying only `target_id`,
       then only `project_id` — so an index keyed on `project_id` alone, or on `target_id`
       alone, fails one of them.
   - [ ] Confirm fails: the second `EnqueueTask` in case 1 succeeds and
         `ListQueueByProject` returns 2 rows, not 1 — the plain `INSERT` with no index writes
         a duplicate today.
